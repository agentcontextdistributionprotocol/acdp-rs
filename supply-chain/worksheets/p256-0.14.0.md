## Arithmetic backend (what ACDP actually compiles)

- **Field** (`src/arithmetic/field.rs`): Montgomery-form elements built with the
  `primefield::monty_field_params!` / `monty_field_element!` macros over
  `crypto-bigint` 0.7 `U256`, with hand-written add/sub/Montgomery-reduce in
  `field/field64.rs` or `field/field32.rs`. Masked conditional modulus addition
  (`sub_inner`), fixed-index limb arrays only. `sqrt` (p ≡ 3 mod 4 exponentiation) returns
  `Some` only if `sqrt² == self` (`:142-146`).
- **Scalar** (`src/arithmetic/scalar.rs`): `Scalar(U256)` with crypto-bigint
  `add_mod`/`sub_mod`, Barrett reduction in `scalar/scalar64.rs` / `scalar32.rs`,
  `invert` via `invert_odd_mod` and `invert_vartime` via `invert_odd_mod_vartime`.
  `from_repr` rejects values `>= n` (`:306-311`); `is_high` compares against `(n-1)/2`.
- **Word size:** `cpubits!` (cpubits 0.1.1) picks 64-bit limbs on x86_64 and aarch64 and
  **also on wasm32** (cpubits treats wasm32 and armv7 as 64-bit), so every ACDP artifact
  compiles the `*64.rs` files; `*32.rs` would need a 32-bit non-wasm target or
  `--cfg cpubits="32"`.
- **Scalar multiplication:** `precomputed-tables` is off, so `Backend = VariableOnly`
  (`src/arithmetic.rs:47`), whose defaults (`primeorder` `mul_backend.rs:10-41`) are
  `GENERATOR * k` for signing and a vartime `lincomb_vartime` for `u1·G + u2·Q` in
  verification.
- **Constant time (not claimed):** choices use `subtle`/`ctutils` (`Choice`, `CtOption`,
  `ConditionallySelectable`) and crypto-bigint 0.7's constant-time-intended limb ops; the
  vartime paths (`invert_vartime`, `lincomb_vartime`, `pow_vartime`, `sqn_vartime`) operate on
  public data in verification or on constants. This review does not establish that the
  generated code is constant-time.

## How ACDP uses P-256 (call sites)

ACDP **signs as well as verifies** with P-256; the plan's "verification only" wording is
inaccurate (finding P-3).

- **Verify:** `acdp_crypto::verify::verify_ecdsa_p256` (`crates/acdp-crypto/src/verify.rs:41-65`):
  `VerifyingKey::from_sec1_bytes(pub_key_sec1)` -> base64 decode -> length must be 64 ->
  `Signature::from_slice` -> `key.verify(message.as_bytes(), &sig)`, i.e. SHA-256 of the
  ASCII `content_hash` string, then ECDSA verify (ecdsa worksheet, "Hash-then-verify").
  Called from `acdp-verify` (`src/lib.rs:230,273,400`), receipt and lifecycle
  verification (`acdp-types` `receipt.rs:115`, `lifecycle.rs:423`).
- **Key material sources:** `did:web` JWK -> `0x04‖x‖y` after checking both are 32 bytes
  (`crates/acdp-did/src/document.rs:198-226`); `did:key` -> 33 bytes with an explicit
  `0x02|0x03` tag check (`crates/acdp-did/src/key.rs:91-104`).
- **Point validation:** `from_sec1_bytes` -> `sec1` tag/length check -> `primeorder`
  `AffinePoint::from_sec1_point`: uncompressed points are checked on-curve
  (`affine.rs:100-108`, coordinates range-checked by `FieldElement::from_repr`);
  compressed points are decompressed with a checked square root (`affine.rs:183-198`);
  the identity encoding is rejected by `PublicKey::from_sec1_point`
  (`elliptic-curve` `public_key.rs:188-194`). P-256 has cofactor 1, so an on-curve,
  non-identity point is in the prime-order group.
- **Sign:** `P256SigningKey` (`crates/acdp-crypto/src/sign.rs:123-277`): `generate` via
  `SigningKey::generate_from_rng(UnwrapErr(getrandom::SysRng))` (`:130-139`),
  `from_bytes` (`:147-151`, rejects 0 and `>= n`), `sign_content_hash` / `sign_string`
  (RFC 6979, r‖s via `Signature::to_bytes`, `:169-208`), and `seed_bytes` (`:187-193`).
- The `sig-002` conformance tests (`tests/conformance.rs:1346,1369`) are behavioural
  evidence only.

## Findings (ACDP-relevant; not vet concerns)

### P-1: ECDSA-P256 signatures are malleable; high-S is accepted

- `NORMALIZE_S = false` (`src/ecdsa.rs:60`), so `ecdsa::hazmat::verify_prehashed` accepts
  both `(r, s)` and `(r, n-s)` for the same key and message. ACDP's own signer does not
  normalize either, so roughly half of ACDP-produced P-256 signatures are high-S.
- The ACDP signature-algorithms registry (`registries/signature-algorithms.md`,
  `ecdsa-p256` wire form) defines r‖s and recommends RFC 6979 but says nothing about low-S.
- **Impact:** a third party without the key can turn any valid `signature.value` into a
  different valid one over the same `content_hash`. Signature validity is unaffected, but
  anything that treats `signature.value` bytes as a unique identifier (dedup, idempotency
  keys, log entries that commit to the signature bytes) must not assume uniqueness for
  `ecdsa-p256`. One ACDP place that does: the lifecycle-event retry check compares whole
  events with `prior == event` (`crates/acdp-server/src/registry/store.rs:585-596`), which
  includes `signature.value`, so a retry whose signature was flipped to high-S gets a
  `SchemaViolation` instead of `IdempotentReplay` (low impact: no forgery, the stored event
  stays valid). Publish idempotency is keyed on `content_hash` (`store.rs:724`) and is
  unaffected.
- **Options:** (a) document non-uniqueness in the spec registry entry (no code change);
  (b) have ACDP signers emit low-S (`Signature::normalize_s`) while verifiers keep
  accepting both; (c) require low-S at verification, which would reject existing
  high-S signatures. Recommendation: (a), plus (b) as a cheap producer-side improvement;
  this is a spec question, not a supply-chain one.

### P-2: `VerifyingKey::from_sec1_bytes` also accepts the SEC1 "compact" tag `0x05`

- `sec1` 0.8 `Tag::from_u8` accepts `0x00, 0x02, 0x03, 0x04, 0x05`
  (`sec1-0.8.1/src/point.rs:527-536`); a 33-byte `0x05‖x` input decodes through
  `AffinePoint::decompact` to a valid curve point.
- Every in-tree resolution path pre-shapes the bytes (`0x04` from a JWK, `0x02|0x03` checked
  for `did:key`), so wire input cannot reach this. Only direct callers of the public
  helpers `verify_ecdsa_p256`, `fingerprint_p256_sec1`, and `did_key_from_p256_sec1`
  with raw bytes could pass a `0x05` encoding, and it would denote a real key. The same
  holds for the operator-pinned key path (`crates/acdp-server/src/registry/server.rs:1636`)
  and the bindings' `verify_signature_p256`; this is benign because the key fingerprint is
  computed over the re-compressed point (`fingerprint.rs:27-35`). Informational.

### P-3: the plan's "P-256 for verification only" statement is inaccurate

- ACDP generates, loads, exports (`seed_bytes`), and signs with P-256 keys (see call
  sites). The review therefore covered the signing path too.
- **ACDP-side hygiene (our code, not the crate):** `P256SigningKey::seed_bytes`
  (`sign.rs:187-193`) copies the secret scalar through a non-zeroized `FieldBytes`
  temporary (`fb`) into a plain `[u8; 32]` return value. The returned copy is the
  documented contract (bindings rebuild the key per call), but the intermediate `fb`
  could be wrapped in `zeroize::Zeroizing`. The comment at `sign.rs:279-281` says the
  inner `Scalar` "implements `ZeroizeOnDrop`"; precisely, `ecdsa::SigningKey` has an
  explicit `Drop` that zeroizes its `NonZeroScalar` (ecdsa worksheet).

## Zeroize interplay (zeroize 1.9.0 remains exempt, DECISIONS.md `322-zeroize`)

- `Scalar: DefaultIsZeroes` (`src/arithmetic/scalar.rs:336`); `Scalar` is `Copy` over a
  `U256` limb array (no padding), so zeroize's volatile write plus barrier operate on fully
  initialized memory and Z-1 is not triggered, including on the wasm32 binding.
- p256 has no other `Zeroize` impl, no `Option<Z>` / `MaybeUninit` zeroization.
  Barrier efficacy is zeroize's property, not claimed.
